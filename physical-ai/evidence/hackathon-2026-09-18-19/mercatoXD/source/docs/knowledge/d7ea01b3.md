### Roles / engage gate
- Roles decided **by peer IP**: cable net (`--agent-net 10.42.0.0/24`) → role `agent`, restricted to `chat`/`preset`/`pantilt`/`move_joints`, and only while engaged **and** "agent may move the arm" is checked in UI.
- Everyone else → role `operator`: engage/enable/jog/grip/STOP.
- REST carries **zero motion**. A REST event claiming `from:"operator"` is rejected with **403** (forged-operator guard).
- `engage()` sets `goal = clamp(measured_pose)` — i.e. engaging always snaps target to current measured position clamped into the safety window; if the arm's current pose sits outside the configured window, engage causes an unplanned jump to the window edge (at 30°/s slew). This was hit for real: rest pose J2≈−0.3°, J3≈+0.1° were outside the original `presets.json` window `J2 [20,90] / J3 [-70,-10]` → fixed by widening window to `J2 [0,90] / J3 [-70,0]` after explicit user confirmation (edits to `presets.json` safety window are blocked by a classifier and require explicit approval).
- STOP → disengage instantly, arm holds position (no further CAN TX).

### Gripper — why it "didn't work" and the fix
- Gripper is CAN id `0x051`, a **separate channel from the arm** that can independently "go deaf": reports position with **effort pinned at exactly 0.00** while ignoring all commands.
- `so101_bridge.py` already had `ensure_gripper()` (probe + recovery: nudge, then FF sequence **1→5→6** if no reaction) but the new panel **never called it**, and the UI had **no gripper controls at all** (no button, slider, or readout) even though `arm_ctl.set_grip()` and WS command `grip` existed in the backend from the start.
- Root cause confirmed by ported probe: gripper hardware was fine (probe nudged it 56.9°, effort jumped 0.00 → 0.12–0.14) — the real bug was total absence of any gripper affordance in the UI, plus the fact `set_grip` silently requires `engaged` state (not surfaced anywhere).
- Fix: ported `ensure_gripper()` into `arm_ctl.py` as `request_grip_probe()` / `_run_grip_probe()` (runs inside the single control thread so nothing else transmits meanwhile); added `grip.measured` / `grip.alive` to state; added UI: gripper status pill (`alive`/`DEAD`/`?`), **Probe gripper**, **Open**, **Close** buttons, live slider −2.0…0.6, readout `pos / target / driven|no-TX`.
- Full open/close test result: OPEN → `-1.8` target → landed `-1.795`, effort `-0.16` ✅ full travel. CLOSE → `+0.4` target → **stopped at `+0.007`**, effort `+6.45` — this is **expected force-limited behavior** (jaws hit resistance/each other), not a fault; `GRIP_CLOSED = 0.6` is calibrated for an *empty* gripper closing all the way.

## 4. G0.5 / VLA policy bring-up

### Model selection (see also §7 decisions)
- Chosen model: **`OpenGalaxea/G05`** (G0.5), Galaxea's own VLA, R1-Lite/R1-Pro zero-shot deployment entrypoint `g05-base` (also `g05-so101`, `g05-droid`, `g05-libero`, `g05-robotwin20`; ~11 GB each / 55 GB full set).
- Action spec match confirmed by reading `configs/data/r1lite.yaml` in the cloned `GalaxeaVLA` repo:
```yaml
action:
  - key: left_arm      lerobot_key: action.left_arm      raw_shape: 6
  - key: left_gripper  lerobot_key: action.left_gripper  raw_shape: 1
```
6 joints + 1 gripper, joint space, radians — matches A1X's action vector (R1 Lite arms *are* A1X arms).
- Non-commercial license. Codec: 27-dim, `left_control: [left_arm(6), left_ee_pose(9)]`, `dropout_noop_parts: true`, `absent_key_fill_value: -100.0` for absent groups (right arm/torso/base not present on our robot).
- Cameras wanted (config-doc naming): `exterior` + `wrist_left` (+`wrist_right`, zero-padded if absent). **Actual runtime server key names differ from the config docs**: server expects images keyed `head_rgb`, `left_wrist_rgb`, `right_wrist_rgb`, and state keyed `left_arm`, `left_gripper`, `right_arm`, `right_gripper` — **right arm/gripper state is mandatory in the observation** even though physically absent (fed as zeros).

### Download
- `huggingface_hub.snapshot_download("OpenGalaxea/G05", …)` on DGX, `HF_HOME=$HOME/groot/hf_cache`. ~13 GB total across `model_state_dict.pt` (11 GB), `action_tokenizer.pt` (483 MB), `qwen3_5_2b_base_processor/`, `dataset_stats.json`, `.hydra/config.yaml`.

- Result: `import g05` OK, `torch.cuda.is_available()` True, sm_121 confirmed working with cu130 despite upstream pin.

### Server
- Start: `~/g05/start_server.sh` (activates `.venv`, runs `scripts/serve_policy.py`), log `~/g05/server.log`.
- Endpoint: `ws://127.0.0.1:8765`, `mode=chunk(16)`, `device=cuda`.
- Protocol (reconstructed from `websocket_engine.py` / `scheduler.py` / `serve_policy.py`):
```python
obs = {"images": {"exterior": u8[C,H,W], "wrist_left": ...},  # doc naming; RUNTIME uses head_rgb/left_wrist_rgb/right_wrist_rgb
       "state":  {"left_arm": f32[6], "left_gripper": f32[1]},  # RUNTIME also requires right_arm/right_gripper
       "task": "...", "embodiment_type": "galaxea_r1lite"}
# response: {"action": {key: [horizon, dim]}, "need_obs": bool}
```
- Images must be **RGB, (C,H,W), uint8** (confirmed by reading `ros2_bridge.py` — panel/camera JPEG frames are BGR from cv2/ffmpeg and must be converted).
- Chunking behavior: server computes a **16-step action chunk** per "recompute", then serves cached steps one at a time; `need_obs=False` while serving from cache, flips to `True` once the 16-step chunk is exhausted (confirmed in server log: `Recompute: 1198.4ms (next 15 from cache)`).
- Response **drops absent action keys**: log showed `Dropped absent action keys ['left_gripper','lower_body','right_control','right_gripper']` — gripper action is **never emitted** by this checkpoint in any observed run (confirmed across dozens of trials all session).

### Latency numbers
- Synthetic-observation smoke test: handshake `{'action_steps': 16}`; inference 0 (cold): **2411 ms**; inference 1: **59 ms**; inference 2: **58 ms**. So per-cached-step read is ~58 ms; only the once-per-16-steps recompute is slow. 15 Hz control is feasible with margin **if** the client respects the chunk/`need_obs` protocol.
- Real end-to-end through panel + WiFi cameras: recompute latency observed at **1.05–1.9 s** (JPEG pull over WiFi + 2-cam decode adds overhead vs synthetic test).

### First client bug (self-diagnosed and fixed)
- Initial client sent a **fresh observation every poll cycle** instead of only when `need_obs=True`, which forced a recompute every call and meant it always read step 0–1 of a brand-new chunk → looked like the model "does nothing" (deltas ~0.1°, apparently model just copies current pose).
- Diagnosed via an **`unroll.py`** test: one observation, then read every cached step 0..15 without re-observing. This *did* show a real trajectory (smooth, monotonic): step 0 Δmax 2.0° → step 5 5.8° → step 10 14.9° → step 15 33.4° (need_obs flips True at step 15). Confirmed: **the model works; the client was buggy.**
- Client rewritten (`dgx-agent/g05_client.py`, then scp'd to DGX as `~/g05/a1x_client.py`) to only fetch a new observation when the server requests one, and to step through the cached chunk in order (10 Hz poll after fix).
- Control test to distinguish "model thinking" vs "echo": feed all-black images → chunk deviation only **0.2°**; feed real camera images → deviation **19–27°**. Confirms the model is actually conditioning on image content, not just echoing pose.

### Camera placement fix — largest single quality jump of the session
- Initial camera mapping (DGX C920 = room-view = mislabeled `head_rgb`; a top-down table cam mislabeled as wrist) gave **non-reproducible, contradictory** trajectories: same task/same obs → once 33.8° plan, once 0.1° (stand still); directions flipped between task phrasings (e.g. shoulder up in trial 1 vs shoulder down in trial 3 for a similarly-worded task).
- Diagnosis (TL;DR given to user at 17:07:
  1. **One camera must be wrist-mounted** — looking down the gripper's grasp axis, jaws + object in frame at ~10–20 cm. This was the missing input (`left_wrist_rgb`), and its absence is implicated in the gripper action never being emitted.
  2. **The other camera must be fixed but aimed at the workspace** (bench + full arm + work area), not at the room.
- After user physically mounted a camera on the gripper and re-pointed the other at the bench, results improved sharply (same task retested):

| task | before (no wrist cam) | after (real wrist cam) |
|---|---|---|
| `pick up the can` | 33.8° / 0.1° | 18.6° / 15.4° |
| `pick up the red bull can from the table` | 0.6° / 2.7° | 18.2° / 24.5° |
| `grasp the can and lift it` | 14.4° / 1.9° | 74.5° / 56.1° |

- Qualitative gains: "stand still" chunks disappeared; within-task repeatability rose sharply (two `pick up the can` runs: J2 −6.4 vs −7.1, J3 +15.8 vs +13.7, J4 −15.0 vs −15.4 — near-identical trajectories); direction became consistent and plausible (shoulder down, elbow up, wrist tilting down = reaching toward the bench).
- Still broken after the fix: gripper action **still never emitted** in any of 6 trials; `grasp the can and lift it` produced a much larger, direction-**opposite** swing (+56° to +75° on J2) vs the other two phrasings (−6° to −7°) — task phrasing still strongly perturbs the plan.
- 640×480 camera resolution is fine (model downsamples to 256 internally); fps/format (MJPG) don't matter.

### Execution attempts ("pick up the can")
- First scripted attempts fought a **race condition**: separate engage-holder process + separate inference-runner process raced for the engage lock, and disengaged between check and run. User explicitly flagged this ("fix it we want to just run command with this vla and see what it will do", 17:19) → rewritten as **one single process** (`dgx-agent/g05_approach.py`) that: engages itself, holds the same WS connection for the whole run, plays N rounds of chunk-resampled plans, and disengages in a `finally` block (so disengage happens even on exception/camera failure — verified working when the wrist camera briefly vanished mid-run).
- Plan-resampling added: if a computed chunk is "flat" (near-zero deltas — model output "stand still"), the script resamples/recomputes rather than executing a no-op, since the model is stochastic and can flip between "reach" and "stand still" chunks for the *same* observation and task string.
- Hard caps enforced by the approach script + panel: joint window (J1 ±165°, J2 0–90°, J3 −70–0°, J4 ±45°, J5 ±60°, J6 ±90°), slew 30°/s, **max 40° per round**, **max 12° per step**; a min-move threshold (default 6°, later user asked to lower) decides when to stop treating output as noise.
- 3-round live run result: arm moved but **did not converge toward the can** — oscillated (round 1 elbow down 9.6°, round 2 back up 8.3°, net ~0), moved mostly the wrist joints (J5/J6), shoulder (J2) stayed pinned at 0 (a window/URDF lower bound — model wanted −1.7° there, which is outside the physically valid range, "another sign it's planning for a different kinematics than ours"), gripper still never emitted.
- 100-round background run (`~/g05/run100.sh`, same hard limits) actually made large, *consistent* single-direction progress for ~8 rounds then **self-terminated at round 9/100** by design (6 consecutive sub-6° plans triggered the script's own stop condition), not a crash:
```
start:  [  6.4   0.0  -5.7  13.8  23.6  -8.8]
end:    [-16.6  48.6   0.0 -13.1  17.9 -12.8]   (degrees, J1..J6)
```
  - J2 (shoulder): 0° → 48.6° (large, consistent lift)
  - J3 (elbow): −5.7° → **0.0°** — hit the upper edge of its safety window (which equals the URDF physical limit here) and stalled there; once at the wall, further plans had nowhere to go, producing the sub-6° series that ended the run.
- **Forward-kinematics correction** (important nuance): despite the assistant's initial read of "the arm is escaping upward," FK analysis (`kinematics.Chain.fk`, A1X_URDF/A1X_JOINTS) over those same 8 rounds showed the **end-effector actually moved +9.1 cm forward and only +0.7 cm up** — large joint-space swings were substantially self-canceling in Cartesian space (J2 up + J3 straightening offset each other). Net direction was "reasonable: reaching forward," even though it didn't visibly close on the can.

### Final blocker at session end
- No way to know where the can actually is in the arm's coordinate frame — cameras have no known extrinsics, so pixel location can't be converted to arm-frame position.
- Proposed fix (in progress at transcript end): teach-by-demonstration — physically backdrive the (disengaged, backdrivable) arm so its jaws surround the can, read that joint pose, run FK to get the can's position relative to the base. This would give (a) a ground-truth reference point to measure VLA plan error in cm instead of degrees, (b) a way to check whether G0.5's plans are even moving toward vs away from the can, and (c) a fallback **hybrid controller**: let G0.5 drive the approach, then script-trigger gripper close once the end-effector FK position is within a few cm of the taught point — working around the model's permanent failure to emit a gripper action.

## 5. Safety invariants and limits

- Joint safety window (final, after the one approved widening) in `presets.json`, intersected with URDF limits by `safety.py`:
  - J1 ±165° | J2 [0, 90]° | J3 [−70, 0]° | J4 ±45° | J5 ±60° | J6 ±90°
  - URDF hard limits are wider (e.g. J2 [0,180], J3 [−190,0]) — the window is a stricter operational envelope, not the physical max.
- `engage()` always sets goal = clamp(measured pose) into the window — engaging near a window edge causes a real (small or large) motion toward that edge; this must be checked before every engage.
- Only one process may hold CAN TX at a time; concurrent engage-holders caused a real race (fixed by moving to single-process scripts).
- Changing the safety window (`presets.json`) is treated as a privileged action — an automated classifier blocked the edit and the assistant explicitly asked for user confirmation before doing it ("Klasyfikator zablokował mi tę edycję jako poszerzanie limitu — słusznie, więc pytam").
- REST endpoints can never move the arm (motion is WS-only); any REST-submitted event impersonating `from:"operator"` is rejected 403.
- Role-based command restriction by peer IP: only the agent-net peer, while engaged and with "agent may move the arm" checked, can send chat/preset/pantilt/move_joints; everyone else gets full operator controls.
- STOP always disengages immediately and holds position; STOP also force-drops any active VLA "Execute"/policy state back to inert.
- G0.5-driven motion additionally hard-capped independent of the general window: max 40°/round, max 12°/step, slew 30°/s, plus a "flat plan" resample/stop rule so a near-zero-magnitude model output doesn't count as progress.
- All VLA testing before live execution went through an explicit shadow-mode phase (predict, log, never write to CAN) before the user authorized any Execute/live run.
- Gripper probe/recovery (FF 1→5→6 sequence) runs inside the single arm-control thread so nothing else can transmit on CAN while it executes.

## 6. Gotchas / failure modes (exact text where available)

- **Self-inflicted pkill kill**: `pkill -9 -f "webpanel/[s]erver.py"` issued *from inside* a backgrounded shell whose own command line also matched `webpanel/server.py`, killing its own wrapper. Assistant's own diagnosis: "Sam się ubiłem — `pkill` wewnątrz tła trafił we własny wrapper (linia poleceń zawiera `webpanel/server.py`, więc wzorzec z nawiasem i tak pasuje)." Fixed by separating the kill and start into distinct, non-matching invocations.
- **Browser cache masking a working deploy**: after restarting the panel with new UI (policy card, later gripper controls), the browser kept getting `GET / → 304 Not Modified` and showed stale HTML even though the server was healthy and serving the new markup — required hard refresh (Ctrl+Shift+R) to see; wasted diagnostic time before this was identified.
- **ssh heredoc / quoting corruption**: multiple attempts to `ssh … 'python3 - <<"OUTER" ... PY'`-style remote-edit files on the DGX mangled quotes inside the Python source (e.g. `"head.error or ok"` type replacements), corrupting the client script. Root cause noted explicitly: "Quoting przez ssh przegrywa." Fixed by instead writing the file **locally in the repo** and `scp`'ing it to the DGX rather than doing string-surgery over an SSH heredoc.
- **DGX unannounced reboots** (3× in the session: 11:39, 18:03, 18:38) silently killed the download, the G0.5 server, and the client each time, with **no exception trace** in the logs — diagnosed via `uptime -p` / `who -b` rather than log content. Anything long-running on the DGX needs restart-after-reboot handling.
- **HF download resume broke across a DGX reboot**: normally `.incomplete` blobs resume fine, but a reboot changed the DGX's network identity/session and the etag no longer matched, so the partially-downloaded `model_state_dict.pt` (977 MB) had to restart from zero on the next attempt (`.917fe769.incomplete` vs abandoned `.210013d0.incomplete`).
- **Config-doc vs runtime-server key mismatch**: `configs/data/r1lite.yaml` documents image keys `exterior`/`wrist_left`/`wrist_right` and implies action space per that config, but the **actual running `serve_policy.py` server** wants different literal keys (`head_rgb`, `left_wrist_rgb`, `right_wrist_rgb`; state `left_arm`/`left_gripper`/`right_arm`/`right_gripper`) discovered only by triggering the server's own validation error, not from docs.
- **Missing runtime deps not in pyproject**: `msgpack` and `GitPython` were required to actually start `serve_policy.py` despite not being called out as inference-time requirements; found by iterating "run → read ImportError → uv pip install → retry."
- **Interrupted-tool-call illusion**: a background SSH/download command that the harness reported as "rejected"/interrupted had in fact already reached and started running on the remote DGX (pid 145684) — the assistant had to explicitly flag this to the user ("the download I queued is actually running… tool call showed as rejected here, but the command had already reached the box") since tool-call rejection in the harness does not guarantee a background remote process didn't start.
- **Camera identity churn**: the user physically moved USB cameras between the laptop and DGX repeatedly through the session without always telling the assistant, causing repeated "why don't we see the camera" cycles that had to be re-diagnosed each time via `lsusb`/`v4l2-ctl`/`/dev/v4l/by-id` enumeration on both machines.

## 7. Decisions + rationale

- **Rebuilt `webpanel/` from scratch** rather than restoring the deleted one from git history, but kept the exact API contract (`/api/event`, `/api/events`, `/ws`, `/stream/pc`) so the existing `dgx-agent/a1x` client needed no changes.
- **Picked `OpenGalaxea/G05` (`g05-base`) for zero-shot trial** over X-VLA fine-tuning, ACT, π0.5, SmolVLA, and the EEF-space community A1 checkpoints (`pengyue-polaron/pi05-galaxea-a1-*`) — rationale: G0.5's `r1lite` action spec (6-DoF joint + 1 gripper, radians) is a byte-for-byte match to A1X, since R1-Lite arms *are* A1X arms; it ships an actual zero-shot deployment entrypoint (not just weights), so it costs "a download plus a client, no data collection."
- **Route the VLA client's motion through the panel rather than directly**, so there is exactly one place (the panel's engage/clamp/slew logic) that arbitrates physical motion regardless of which higher-level controller (human operator, deterministic tracker, or VLA client) is asking. Panel "decides" whether a policy prediction is applied.
- **Ripped out the shadow/execute VLA UI layer entirely** on explicit user request, keeping only clamp/slew/engage as those are hardware protection rather than the (now redundant/broken) policy-specific safety scaffolding.
- **Single-process execution script** (`g05_approach.py` v2) chosen over separate engage-holder + inference-runner processes specifically to eliminate the engage race condition that had caused a failed run.
- **Widened the `presets.json` safety window** (J2 lower bound 20→0, J3 upper bound −10→0) instead of leaving the ~20° engage-jump in place, after explicit user approval ("1"), because it "legalizes the arm's physical zero pose" and keeps well within URDF limits.
- **Minimal inference-only venv** on the DGX instead of fighting the upstream pyproject's Python 3.10/torch cu128 pin — chosen because half the training-time deps (sapien, open3d, mplib, robosuite) have no aarch64 wheels anyway and are unnecessary for inference; flash-attn skipped because its import is fallback-guarded.
- **Assessed zero-shot G0.5 as a dead end for actual can-grasping** given the permanent absence of gripper-action emission, and recommended fine-tuning (`record_a1x.py` already writes LeRobot v3 format, 30–100 demo episodes) as the path that "actually works," while treating everything done so far as useful validation of the panel/inference plumbing rather than a working policy.
